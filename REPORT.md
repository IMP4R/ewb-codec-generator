# Реверс формата .ewb (Electronics Workbench 5.12) — полная история

Дата работы: 2026-10-01. Цель: программная генерация `.ewb` со схемами «точь-в-точь»
по методическим рисункам, без кликов по GUI.

---

## 1. Исходная проблема

Файл `.ewb` версии 5 имеет вид:

```
Electronics Workbench Circuit File\r\n
Version: 5\r\n
Charset: ANSI\r\n
Description: \r\n
"" \r\n
\r\n
EncryptionType: 2\r\n
UsingVectorGraphics: 0\r\n
/000@D0I0?4D<DHI@3078;L=8?@A404D8@4@8GD7L80@030B88HIHC078=4M040542...
... ещё несколько тысяч символов ...
$!3608f37a
```

Тело — сплошной поток символов из диапазона `0x30..0x4F` (32 символа = 5 бит на символ),
`/` встречается только в позиции 0, в конце `$!` и 8 hex-символов.

Первая гипотеза (шифр с data-dependent потоком) подтвердилась численно, но не объяснила
всё: одинаково пустые схемы, сохранённые в разные моменты, давали разные хвосты.

---

## 2. Экспериментальная база

Собраны пары файлов, отличающихся ровно одной операцией, сохранённые в одной сессии EWB:

| Файл | Что внутри | Размер тела |
|---|---|---|
| `probe1.ewb` | пустая схема | 4488 симв. |
| `probe2.ewb` | пустая + земля | 4686 симв. (+198) |
| `ta.ewb` / `tb.ewb` | одна и та же пустая, интервал 82 с | 4493 / 4487 |
| `t1resaved.ewb` | пересохранение старого формата Type 1 | 4480 |
| `pr1res.ewb` | open→resave пустой схемы | 4490 |

Установленные факты:

* Схемная часть детерминирована: `pr1res` совпадает с `probe1` до символа 2211,
  дальше — мета (timestamp / undo-id), зависящая от состояния приложения.
* Вставка компонента (@1292 в `probe2`) полностью перемешивает хвост: сдвиговый
  поиск по всем выравниваниям даёт максимум 61 % совпадения. Это признак
  self-синхронизирующегося кодека, а не поблочного.
* `UNTITLED.EWB` из поставки имеет `EncryptionType: 1` и алфавит из 16 букв `A..P`
  (4 бита на символ). EWB 5.12 его читает, но пересохраняет всегда как Type 2 —
  старый формат только для входа.
* Файл с `EncryptionType: 0` не открывается вообще («access violation»).

## 3. Дизассемблирование WEWB32.EXE

Образ: PE32, 2185248 байт, image base `0x400000`. Секции:

```
CODE  va=0x10000 vs=0x14a000 ra=0x800      → vaddr = file_off - 0x40F800
DATA  va=0x160000 vs=0x5c000  ra=0x14a400   → vaddr = file_off + 0x415C00
```

> Ошибка в начале работы: я использовал поправку `-0x3FF800` вместо `-0x40F800`,
> из-за чего поиск прологов функций давал мусор. Правильная поправка — `-0x40F800`.

### 3.1 Найденные адреса

| Адрес | Что это |
|---|---|
| `0x486f9e` | экспорт `EwbFileSave` → вызывает `0x486db9` |
| `0x486db9` | внутренняя сохранка: `0x53497b` (сериализация схемы), `0x51cd9a` (расширения) |
| `0x5345fc` | главный сериализатор (11 аргументов), готовит заголовок файла |
| `0x4a9def` | **push_byte** — выдача одного байта plaintext-потока |
| `0x4a9a4d`, `0x4a9aeb` | декодер: чтение символов файла, сборка 5-бит (`add al,0xd0` = −0x30) |
| `0x4a9fd6` | **SOURCE-callback**: компрессор тянет plaintext блоками |
| `0x4aa04e` | **SINK-callback**: компрессор отдаёт сжатые байты |
| `0x4a9e21` | init_save → `0x5582bc` |
| `0x5582bc` | инициализация компрессора, копирует константные таблицы |
| `0x558434` | эмиттер: LZ-окно `[ebx+0x30]`, сброс при 0x2000, вызов `0x55851e` |
| `0x55851e` | **декодер токена**: литерал по трём уровням таблиц, либо матч |
| `0x55875a` | битовый ридер/райтер, LSB-first |
| `0x5587e1`, `0x55881d` | построение канонических таблиц Хаффмана |
| `0x5586db` | длина матча (либо `token − 0xFE`) |
| `0x558280` | обновление CRC32 по прочитанному plaintext |
| `0x599fcc` | таблица CRC32 (полином `0xEDB88320`) — совпадает с zlib |
| `0x598474` | таблица классов символов (22 класса) |

### 3.2 Константные таблицы кодера (в DATA)

| Адрес | Размер | Содержимое |
|---|---|---|
| `0x59a49c` | 256 | длины кодов литералов |
| `0x59a59c` | 256 слов | коды литералов |
| `0x59a3cc` | 64 | длины кодов длин матчей |
| `0x59a40c` | 64 | коды длин матчей |
| `0x59a47c` | 16 | длины кодов дистанций |
| `0x59a48c` | 16 | коды дистанций |
| `0x59a44c` | 16 | число extra-бит дистанции |
| `0x59a45c` | 16 слов | базы дистанций `1,2,3,4,5,6,7,8,10,14,22,38,70,134,262` |

### 3.3 Инициализация компрессора (`0x5582bc`)

Из входного буфера читаются три первых байта:

```
[ebx+0x04] = byte0   → тип кодека (должен быть 1)
[ebx+0x0c] = byte1   → число бит дистанции (должно быть 4..6)
[ebx+0x14] = byte2   → начальное значение бит-буфера
[ebx+0x1c] = 3       → позиция чтения
[ebx+0x10] = 0xffff >> (16 − бит_дистанции)
```

Дальше копируются таблицы (см. выше) и строятся карты `0x2c34` / `0x2d34` /
`0x2e34` / `0x2eb4` — трёхуровневый декодер Хаффмана: сначала пробуем 8-битное
окно, при промахе дочитываем 4, 6 или 8 бит и смотрим в более длинную таблицу.

## 4. ГЛАВНЫЙ РЕЗУЛЬТАТ: тело файла — это читаемый текст

Перехват `push_byte` (`0x4a9def`) дал полный поток plaintext, который EWB отдаёт
компрессору. Формат:

```
Project_5_1
{
  CircuitHeader
  {
    InternalCircuitVersion i 511
    ZoomFactor i 80
    VersionSpecific { SerialNo R "\"RBS-1999-RBS\"" ... }
    ...
  }
  Circuit
  {
    Models { ... }
    Preferences { Mode i 16 ... Fonts { Label { Name R "Arial" ... } } }
    Elements
    {
      Comp
      {
        PartNum i 5
        Position i:3 2 1098 809
        ModelUnits i:1 0
        Common { RefID A "Q1" }
        ModelName R "spice:QN"
        Status i 0
      }
    }
    Wires
    {
      wire
      {
        pos i:4 0 1 7 1
        segs i:6 2 44 4 80 8 20
        colour i 0
        wire_id i 0
        node_p A "1"
        x_factor r 1
        y_factor r 1
      }
    }
    InstSettings { ... }
    SimulationOptions { ... }
  }
}
```

Объём: 5435 байт для пустой схемы, 16295 байт для схемы из 11 компонентов и 6 проводов.

### 4.1 Каталог PartNum (из живого примера 201.ewb)

| PartNum | Компонент | Поля |
|---|---|---|
| `1` | резистор | `Value r:5 <номинал> 0 0 0 0` |
| `2` | источник постоянного напряжения | `Value r:3 <U> 0 0` + блок `IndependentSourceParameters` |
| `5` | биполярный транзистор NPN | `ModelName R "spice:QN"` |
| `8` | земля | `Value r:1 0` |
| `13` | мультиметр (вольтметр) | `Value r:2 1 0` |
| `39` | линия питания (рельс) | `m_tptrElem A "VCC^0"` |

### 4.2 Ключи

* `i <число>` — целое
* `r <число>` — вещественное
* `R "строка"` — строка в кавычках
* `A "строка"` — «идентификатор» (RefID, node_p)
* `i:3 a b c` — массив из трёх чисел (Position: ориентация, x, y)
* `i:6 ...` — массив из шести чисел (segs: длины сегментов провода)
* `r:5 ...`, `r:3 ...` — вещественные массивы (Value)

### 4.3 Чек-сумма

`$!` + 8 hex = CRC32 (полином `0xEDB88320`, таблица `0x599fcc`) от текста-plaintext.
Проверка стандартным zlib не сошлась, потому что CRC считается по потоку до
последнего `}` и с добавлением `0xFFFFFFFF` в начале — точную границу удалось не
вычислить, но алгоритм известен.

## 5. Конвейер генерации (реализован)

Полностью автоматический, без кликов по схеме:

```
наш текст (Project_5_1 {...})
        │
        │  gdb: mmap-буфер, restore /tmp/inject.bin
        ▼
перехват 0x4a9fdd / 0x4aa02b  → memcpy нашего блока в буфер EWB
        │
        ▼
компрессор EWB (свой кодек) → LZ77 + Хаффман → 5-битная упаковка
        │
        ▼
заголовок + тело + CRC → файл .ewb
```

Ключевая скриптовая находка: подмена должна происходить **только на этапе сохранения**.
Если gdb подключён во время `Ctrl+O`, подменяется поток **загрузки**, и документ
открывается пустым.

### 5.1 Рабочий скрипт подмены

```gdb
set pagination off
set architecture i386
handle SIGUSR1 nostop noprint pass
attach <PID WEWB32.EXE>
set $p = (int)mmap(0, 0x40000, 3, 0x22, -1, 0)
restore /tmp/inject.bin binary $p
set $inj = $p
set $idx = 0
set $rem = <размер inject.bin>

break *0x4a9fdd          # вход в SOURCE-callback: edi=буфер, esi=&длина
commands
silent
set $dest = $edi
set $plen = $esi
continue
end

break *0x4aa02b          # выход: подменяем содержимое и длину
commands
silent
if $rem > 0
  if $rem > 1024
    set $n2 = 1024
  else
    set $n2 = $rem
  end
  set $rc = (int)0x54cc10($dest, $inj + $idx, $n2)   # memcpy
  set $idx = $idx + $n2
  set $rem = $rem - $n2
else
  set $n2 = 0
end
set *(int*)$plen = $n2
continue
end
continue
```

### 5.2 Порядок действий

1. EWB запущен, окно настроено (`xdotool windowsize/move/focus`).
2. `Ctrl+O` открыть `z9.ewb` как заглушку (**до** подключения gdb).
3. Подключить gdb со скриптом подмены.
4. `Ctrl+S` — тихое сохранение текущего документа.
5. Скопировать полученный файл под нужным именем.

## 8. Как продолжить

Главный нерешённый вопрос — почему шаблон с семью компонентами не открывается.
Следующие шаги по убыванию трудоёмкости:

1. **Пошаговая дельта.** Брать `plain201.bin` и удалять блоки компонентов по одному
   (пересобирая `Elements` из оставшихся), каждый раз проверяя открытие. Так
   находится первый блок, ломающий файл.
2. **Сверка с каноническим текстом.** Открыть рабочий файл, сохранить его через
   EWB и сравнить построчно с нашим текстом — EWB пишет канонический вид,
   любые отличия покажут, что именно он не принимает.
3. **Проверка `segs` у проводов.** Если блоки `wire` ссылаются на несуществующие
   узлы, разборщик может оборвать разбор секции.

## 9. Дописывание: что выяснилось при отладке конвейера

### 9.1 Заглушка должна быть ПУСТОЙ

Самая частая причина провала — неправильная заглушка. Установлено жёстко:

* если открыть документ **с компонентами**, точка подмены `0x4aa02b` **не вызывается
  вообще** (0 попаданий при включённом счётчике) — EWB идёт другим путём сериализации;
* если открыть **пустой** документ — подмена срабатывает, и это дало единственный
  подтверждённый успех: `z9_injected.ewb` (4672 байта), который EWB открыл и нарисовал
  в нём транзисторную схему, которой раньше в файле не было.

Отсюда практическое правило: заглушка каждый раз копируется заново из заведомо
пустого файла (`samples/probe1.ewb`, 4695 байт). После первой же успешной инъекции
заглушка перестаёт быть пустой и конвейер перестаёт работать — это и выглядело как
«регрессия», хотя на самом деле менялась только заглушка.

### 9.2 Ложные подтверждения

Схема, которую я принял за успешную генерацию инвертора (5 V, 1000 Ом, QN, 0.1 V,
вольтметр), оказалась **самим `201.ewb`**, просто пересохранённым. Признак:
размер менялся на 8 байт — ровно на столько, насколько меняется мета-часть при
пересохранении. Правильная проверка результата — сравнивать размер и содержимое
не «на глаз», а по факту изменения файла **заглушки**: если заглушка изменилась
меньше, чем на размер вставки, инъекция не сработала.

### 9.3 Скрипт с самопроверкой (`scripts/generate/gen8.sh`)

Добавляет счётчик попаданий в точку подмены и печатает их в лог — чтобы пустой
прогон отличать от реального результата без открытия файла вручную.

### 9.4 Ограничение длины

Пла Platz: успешно вставлялись тексты примерно до 5.5 КБ. Попытки на 14 КБ не дали
изменений (инъекция не срабатывала). Точный предел не установлен — возможно, он
связан с внутренним буфером сериализатора на 8192 байт (`0x2000`, который виден
в эмиттере `0x558434` как порог сброса).

## 10. Дописывание: рабочий перехват и его грабли

### 10.1 Правильная точка перехвата — сам вызов `memcpy`

Ранее перехват шёл по входу и выходу функции SOURCE (`0x4a9fdd` / `0x4aa02b`).
Это ненадёжно: внутри функции есть быстрая ветвь, которая при уже инициализированном
состоянии идёт мимо точки выхода. Вход при этом срабатывает (1 раз за сохранение),
а точка подмены — нет.

Решение — перехватить **сам вызов `memcpy` внутри SOURCE**:

```
0x4aa023   push [ebp-4]      ; len
           push [ebx+0x30]   ; src
           push edi          ; dest
           call 0x54cc10     ; memcpy
```

При срабатывании точки находятся аргументы: `[esp]` = dest, `[esp+4]` = src,
`[esp+8]` = len. Меняем src и len — данные подставляются в момент копирования:

```gdb
break *0x4aa023
commands
silent
if $rem > 0
  if $rem > 1024
    set $n2 = 1024
  else
    set $n2 = $rem
  end
  set *(int*)($esp + 4) = $inj + $idx
  set *(int*)($esp + 8) = $n2
  set $idx = $idx + $n2
  set $rem = $rem - $n2
else
  set *(int*)($esp + 8) = 0
end
printf "INJECT hit=%d n=%d idx=%d\n", $n2, $idx
continue
end
```

**Подтверждённый результат:** 6 блоков подмены по 1024 байта, файл записан,
EWB его открыл и выдал точную диагностику в Analysis Graphs:
`Unrecognized file item: 'Comp'`.

### 10.2 Побайтовая реконструкция текста

Достигнута полная побайтовая идентичность исходному тексту, который EWB отдаёт
компрессору: пересобранный файл `v_full.bin` (16295 байт) совпадает с
захваченным `plain201.bin` до байта.

При этом вскрылись две ошибки, каждая из которых ломала разбор:

1. **Завершающий пробел.** Оригинал: `Value r:2 1 0 ` (пробел перед CRLF).
   Регулярка `Value r:\d+ [^\r\n]*` съедала пробел, и разборщик терял строку.
2. **Нарезка блоков.** Поиск закрывающей скобки по шаблону `      }` срабатывал
   и на строке `        }` (отступ 8 пробелов содержит 6 пробелов как подстроку),
   поэтому каждый блок `Comp` обрезался по `Common`, теряя `ModelName` и `Status`.
   Правильно искать `CRLF + 6 пробелов + } + CRLF`.

После исправления обоих пунктов реконструкция стала побайтовой.

### 10.3 Грабля в генераторе скриптов

`sed "s/^set \\$rem = REMHERE$/set \\$rem = $REM/"` **съедал `$rem`** в результате
замены, и gdb падал с `A syntax error in expression, near '= 16295'`, не выставляя
точки вообще. Все прогоны с этой ошибкой были холостыми при нуле счётчика `INJECT`.

Решение — генерировать gdb-скрипт на месте через Python без `sed`
(`scripts/gdb/make_gdb_script.py`).

### 10.4 Правило проверки результата

Счётчик `INJECT` в логе — единственный честный признак того, что подмена состоялась.
Пустой прогон даёт `0` и файл размером с заглушкой. Вид на экране для этого
непригоден: файл может содержать старую схему и выглядеть корректно.

### 10.5 Текущее состояние

Последние прогоны дают 0 блоков даже с тем же текстом, что раньше дал 6 —
EWB перестал отвечать на `Ctrl+S` после многократных перезапусков и открытий.
Механика подмены доказана и воспроизводима; оставшаяся работа — довести
последовательность запуска до устойчивой и сгенерировать схемы лаб.

## 11. Операционные условия, без которых конвейер молчит

Подтверждено серией прогонов: подмена срабатывает **только** при выполнении всех
условий. Нарушение любого даёт `БЛОКОВ ПОДМЕНЫ: 0` и файл без изменений.

1. **Документ должен быть открыт.** Если открыт не тот файл или не открыт ничего
   (заголовок окна `WEWB32.EXE`), `Ctrl+S` не делает ничего.
2. **Открытие нестабильно.** `Ctrl+O` с вводом пути срабатывает не всегда —
   примерно в половине случаев появляется «Could not open file». Нужна проверка
   результата и повтор (до 4 попыток), а также уникальное имя файла на каждый прогон:
   EWB «залипает» на повторном имени.
3. **Диалоги надо закрывать до ввода.** У разных окон кнопка OK в разных местах:
   у «Could not open file» — около (703, 481), у «access violation» — около (703, 423).
   Клик по одной координате промахивается мимо другого окна, и всё дальнейшее
   уходит в никуда. Надёжно — `Return` (активирует кнопку по умолчанию на любом окне).
4. **Шаги открытия и сохранения — разными вызовами с паузой.** В одном скрипте
   стабильности нет: приложение не успевает «устояться» между `Ctrl+O` и attach gdb.
5. **Неизменённый документ не сериализуется заново** — EWB просто оставляет файл.
   Перед `Ctrl+S` документ нужно тронуть.

## 12. Ограничение на объём подмены

При ограничении блока в 1024 байта отработало ровно 6 вызовов (≈6 КБ) независимо от
оставшегося объёма текста: после этого EWB перестаёт запрашивать данные. Значит,
внутренний буфер сериализатора наполняется примерно за 6 КБ.

Варианты обхода, которые ещё не проверены:
* не обрезать длину блока (менять только указатель `src` в `0x4aa023`), чтобы отдать
  весь текст за меньшее число вызовов — скрипт `gdb_inject3.txt` готов, но не доведён
  до проверки из-за нестабильности окружения;
* дробить схему: то, что не влезает в первые ~6 КБ, вынести в отдельный проход.

## 13. Итог

Доказанное и воспроизводимое:
* формат `.ewb` v5 разобран полностью (текстовый слой, каталог компонентов, архитектура кодера);
* текст, который EWB отдаёт компрессору, реконструируется **побайтово**;
* подмена этого текста работает: 6 блоков, файл записан, EWB его читает и выдаёт диагностику.

Недоделанное: довести объём подмены до полного текста схемы и сгенерировать файлы лаб.
Причина задержки — не формат, а нестабильность GUI-автоматизации на сервере после
многочисленных перезапусков EWB.

## 14. Итоговая рабочая схема генерации

Полный цикл, воспроизводящий рабочий результат:

```bash
# 1. Подготовить текст-подмену (мои компоненты + хвост оригинала до точки склейки)
#    точка склейки = начало секции Wires (5289 байт в тексте схемы 201)
#    Моя секция Elements дополняется пробелами ровно до длины оригинальной (3448 байт),
#    чтобы дальше текст совпадал с собственным текстом EWB.

# 2. Перезапустить EWB
pkill -f WEWB32; wineserver -k; sleep 5
cd "/root/.wine/drive_c/Program Files/EWB512"
setsid wine WEWB32.EXE &

# 3. Заглушка — копия схемы нужного размера (201.ewb: текст 16295 байт)
cp 201.ewb invXXXX.ewb
#    Открыть заглушку: Ctrl+O → путь → Enter → Escape
#    (перед Ctrl+O обязательно закрыть флайут Sources: клик по инструменту выделения)

# 4. Подмена: gdb со скриптом splice (перехват memcpy в 0x4aa023,
#    источник — наш буфер, пока не вышли за 5289 байт; дальше — источник EWB)
python3 mkgdb.py <PID> && gdb -batch -x gdb_f.txt &

# 5. Ctrl+S, дождаться, скопировать заглушку под именем результата
```

**Результат:** файл `lab3_1_inverter.ewb` (10342 байта) открывается в EWB и содержит
компоненты инвертора лабы 3: источник 0.1 В (VIN), резистор 10 кОм (Rb), транзистор
QN (Q1), резистор 1 кОм (Rc), линия питания, земля, мультиметр.

**Известный дефект:** провода не подхватываются — разборщик отвергает секцию `Wires`,
потому что точка склейки приходится на середину блока `Comp` (текст, который EWB пишет
при сохранении, отличается от ранее захваченного). Смещение в 5289 найдено по старому
захвату и для текущей сессии попадает внутрь блока компонента.

Проверенные варианты и их результат:
* склейка на 5289 — компоненты грузятся, провода отвергаются, файл валиден;
* склейка на 6531 (вся секция Wires в подмене) — EWB падает при открытии;
* полный текст без склейки, дополненный пробелами или переводами строк до 16295 —
  EWB падает: парсер не терпит ничего после завершающей скобки.

**Как чинить провода:** нужно знать смещение начала `Wires` в тексте, который EWB
пишет при текущем сохранении. Для этого следует захватить текст через `push_byte`
(`0x4a9def`) непосредственно перед подменой и вычислить границу уже по нему.
